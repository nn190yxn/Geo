# AI 可见性运营 Sprint 重构需求

## 背景

当前 GEO 管理平台已具备品牌资料、AI 回复监测、回答分析、内容生成、发布建议和复测能力，但用户视角仍偏功能集合。新阶段需要把这些能力收口为一套“AI 可见性运营 Sprint”闭环，让用户围绕一轮运营目标完成选题、真实回复监测、品牌标准答案对照、缺口诊断、内容补强、发布准备和复测。

## 需求

### R1 Sprint 工作流

- 当用户进入品牌运营工作台时，系统应展示当前 AI 可见性 Sprint 的阶段、状态、关键指标和下一步动作。
- 当 Sprint 未创建时，系统应允许用户基于品牌目标创建一轮 2 到 4 周的运营 Sprint。
- 当 Sprint 运行时，系统应按问题雷达、AI 回复监测、标准答案对照、缺口诊断、内容资产、发布准备、复测看板的顺序推进。

### R2 数据边界

- 系统应清晰区分真实 AI 回复、品牌标准答案和内容资产。
- 系统应仅使用真实 AI 回复或用户手动录入的真实回复计算监测指标。
- 系统应使用品牌标准答案作为对照基准和内容生成依据。
- 系统应使用内容资产记录待发布、已发布和待复测的补强内容。

### R3 问题雷达

- 系统应把问题池组织为面向用户的高价值问题雷达。
- 系统应展示每个问题的意图、平台覆盖、业务价值、状态和是否已进入本轮 Sprint。
- 系统应在同一 Sprint 内按归一化问题文本去重。

### R4 标准答案对照

- 系统应允许为高价值问题生成或维护品牌标准答案。
- 系统应展示真实 AI 回复与品牌标准答案之间的覆盖、准确性、风险表达、引用缺口和竞品压制差异。
- 系统应把对照结果转化为可执行的内容缺口和优化任务。

### R5 内容资产和发布准备

- 系统应从内容缺口生成可审稿的内容资产草稿。
- 系统应展示内容资产服务于哪个问题、哪个缺口、哪个复测目标。
- 系统应生成平台改写版本和发布准备记录，但在真实发布前保持草稿或待人工发布状态。

### R6 复测和趋势

- 系统应为 Sprint 生成复测计划。
- 系统应展示提及率、推荐率、首位推荐率、引用命中率、表达准确率、风险表达数和问题覆盖率等指标趋势。
- 系统应把复测结果关联回问题、标准答案、内容资产和发布记录。

### R7 安全和真实性

- 系统不得把浏览器或模型未真实接入时生成的内容伪装成真实 AI 回复。
- 系统不得在公开 API 响应中返回平台密钥、`credentialRef`、cookies、storage state 或浏览器 profile 路径。
- 系统应在缺少真实回答时阻止分析继续，并引导用户补充真实回复。

## 验收标准

- 共享类型能够表达 Sprint、阶段、状态和指标摘要。
- 后续 API 和前端可基于共享类型实现 Sprint 工作台。
- Sprint 类型不混淆真实回复、标准答案和内容资产。
- TypeScript 类型检查通过。
